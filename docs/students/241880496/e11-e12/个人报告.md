## 2. E11-A：真实基线、缓存投影与目标增量

### 2.1 基线可追溯

固定样例的真实全量图来自 BuildChecker：`make clean` → `strace -ff -s 4096 -e trace=%file,%process` → 解析 Make 数据库，输出 `actual-graph.json`、`findings.json`。流水线把真实图中的对象边投影到基线缓存：

- 缓存 `actual['main.o'] = ['config.h','main.c']`，与真实图边 `main.o → config.h` 一致；
- 该边可回查到 `t.9028` 第 594 行的 `openat` 证据，见 [cache-edge-provenance.json](evidence/e11a-standard/cache-edge-provenance.json)；
- 自主项目 `stats.o → config.h` 同样回查到 `t.9105` 第 692 行，见 [tokenstat provenance](evidence/e11a-tokenstat/cache-edge-provenance.json)。

投影后由 `ecache.scan` 用 `gcc -MM` 重算实际集合，若与真实图不一致立即 `GRAPH_MISMATCH`，不会用 EChecker 的结果冒充 BuildChecker 基线。

### 2.2 目标增量与完整集合对照

固定样例目标提交 `473af31e…` 在 `main.c` 增加 `#include "extra.h"`：

- 失效原因：`['main.c']`；
- 刷新：`['main.o']`；复用：`['helper.o']`（其源码与历史实际依赖未变化）；
- 新增：`MISSING main.o extra.h`；
- 增量发现：`MISSING main.o config.h`、`MISSING main.o extra.h`、`REDUNDANT main.o unused.h`；
- 目标全量发现集合与之逐项相等（不是只比条数）。

自主项目 C2 在 `stats.c` 增加 `extra.h`：失效原因 `stats.c`，刷新 `stats.o`、复用 `main.o`，新增 `MISSING stats.o extra.h`；增量集合 `{config.h, extra.h}` 与全量一致（[incremental-report.json](evidence/e11a-tokenstat/incremental-report.json)、[target-full findings](evidence/e11a-tokenstat/target-full-findings.json)）。

### 2.3 配置化目标/规则映射

课程样例写死 `main.o/helper.o`、`./app`、`1→2`、`config.h`。本人在目标提交根部新增 `e11e12-project.json`，由 `project_config.py` 校验并加载：

```json
{
  "targets": {"main.o": "main.c", "helper.o": "helper.c"},
  "clean_target": "clean", "build_target": "app", "test_target": null,
  "program": ["./app"], "expected_output": "1",
  "header_change": {"file": "config.h", "before": "#define VALUE 1",
                    "after": "#define VALUE 2", "expected_output": "2"}
}
```

`targets` 决定声明图规则与 `gcc -MM` 的 `-MT` 对象；`clean/build/test` 与 `program` 决定全量检测、修复验证的命令；`header_change` 决定动态重检的故障变化条件。未提供配置时保留原 `main.c/helper.c/config.h` 课程契约，旧样例不失效。

## 3. E12：五阶段、同镜像与交接

### 3.1 同 `job_id` / `trace_id`

固定样例和真实项目都是 `draft → full-check → incremental-check → repair → recheck` 五阶段，所有阶段信封带同一 `job_id`、`trace_id`，`full-check` 对应 base commit，其余阶段对应 target commit。见 [E12 固定样例 result](evidence/e12-standard/result.json) 与 [E12 真实项目 result](evidence/e12-tokenstat/result.json)。

### 3.2 DRAFT 镜像实际执行

仅把 `image_id` 写进 JSON 不能证明执行环境已交接。本人的 `draft_exec.ImageExecutor` 用 DRAFT 构建出的镜像启动新容器，绑定同一仓库路径，在其中执行：

- BuildChecker 全量检测（`python3` + `strace`）；
- EChecker 增量扫描（容器内 `gcc -MM`、`gcc --version`）；
- 补丁验证中的 `make`、程序运行和动态重检扫描。

每个命令都保存镜像 ID、完整命令、工作目录、退出码和输出，见 [固定样例 baseline-scan](evidence/e12-standard/baseline-scan/01.json)、[target-scan](evidence/e12-standard/target-scan/02.json) 与 [真实项目 target-scan](evidence/e12-tokenstat/target-scan/02.json)。DRAFT 两轮构建：第 1 轮 `MISSING_MAKE`，第 2 轮成功并运行输出符合预期（固定样例 `1`，真实项目 `config=1 words=7 lines=3`），两轮日志和镜像 ID 在 [draft-build-result.json](evidence/e12-standard/draft-build-result.json)。

### 3.3 报告交接与修复

`repair.json` 的 `data.input_report` 指向本轮 `incremental-check.json` 产物及其 SHA256，不再手工塞固定 MD 文件。补丁只补 `MISSING` 边：

- 固定样例：`main.o: main.c unused.h` → `main.o: main.c unused.h config.h extra.h`；
- 真实项目：`stats.o: stats.c stats.h` → `stats.o: stats.c stats.h config.h extra.h`。

验证结果 `accepted=true`，回滚参数正确；最终全量重检无 `MISSING`，`REDUNDANT` 可保留。真实验证记录见 [validation.json](evidence/e12-tokenstat/validation.json)：`config=1 words=7 lines=3` → 改头文件后 `config=2 words=7 lines=3`。

### 3.4 共享 API

`server.py` 在服务容器内监听 `0.0.0.0:8080`，宿主只绑定 `127.0.0.1:18080`。提交 `mode=e12` 请求后：

- `POST /v1/jobs` 返回 202 和 `job_id`；
- 轮询到 `SUCCEEDED`；
- `GET /v1/jobs/<id>/artifacts` 取得清单；
- 下载 `incremental-check.json`、`repair.json`、`recheck.json`、`candidate.patch`、`validation/validation.json`，文件 SHA256、响应头 `X-Content-SHA256`、清单 SHA256 三处一致（[download-checks.json](evidence/api/download-checks.json)）；
- 同键同输入返回同一任务，同键改 target 返回 `409 IDEMPOTENCY_CONFLICT`（[idempotency.json](evidence/api/idempotency.json)）。

API 任务的 DRAFT 镜像 ID 与 CLI 固定样例不同（每次任务独立构建候选镜像），但同一任务内检测、修复、复验始终使用该任务的 `image_id`。
